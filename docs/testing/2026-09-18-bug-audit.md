## 已修复

### 1. 事务日志内的绝对路径被无条件信任（`0409b74`）

`.skill-studio-replace-*.json` 由 gitignore 排除而非隐藏，会随仓库 clone 流转。启动时
`load_config`（`studio.rs:74-89`）遍历每个已绑定项目的 agent 目录，`linker.rs:377-391`
**只按文件名**匹配这类文件，交给 `transaction::recover` 执行其内容里的绝对路径；
`finish()` 对未提交日志走 `remove(&entry.target)`，而 `remove()` 对目录用
`fs::remove_dir_all`。把带构造过此类文件的仓库绑成项目，下次启动即按文件内容递归删除
任意路径（`existed: true` 时改为把指定备份重命名覆盖到指定目标）。

修法：新增 `recover_confined`，只用于扫描不可信目录的那个入口，要求每个 target 与 backup
都是日志所在目录的直接子项；越界记日志并原样留下文件，不执行、也不返回 `Err`（`load_config`
会把错误上抛，报错等于把任意删除换成应用起不来）。store 级日志继续走原 `recover` —— 它们
按固定路径打开，且合法地跨目录 reserve。

### 2. `paths_overlap` 漏掉末段 symlink（`75e5fd1`）

hub 末段是 symlink 时三级判定全落空：hub 指向 `…/b`，agent 目录是 `…/b/skills`，两者
canonicalize 后不相等、`…/a/link` 不是 `…/b/skills` 的文本前缀、而第三级 `canonical_entry`
只解析父目录、末段原样拼回。于是 `ensure_distinct_roots` 在 8 个调用点（含用户手选 Hub 目录）
全部放行，而 `linker.rs` 模块头把「Hub 不能与任何 agent skills 目录重叠，否则同步会自己
吃自己」列为安全底线第 4 条。

修法：第三级改用 `resolved_entry` —— 整条能 canonicalize 就整条解析，失败才退回父目录解析
（悬空 symlink 是 `canonical_entry` 当初存在的理由，必须保留）。

### 3. 事务性写入丢掉备份（`4a87500`）

`rotate_backup` 从 config.json 当前内容复制，开头有 `!current.is_file()` 守卫；而 5 个调用点
都是先 `tx.reserve(config_path)`（内部 `fs::rename` 把文件挪到兄弟位置）再 `save_config`。
于是分组切换、Hub 托管/还原、项目写入、手动策略 reconcile、目录安装这 5 个最该能回退的操作，
`backups/` 里一份都不留 —— 正是 `store.rs` 模块文档承诺要防住的事。

修法：新增 `Store::reserve_config`，把「先备份、再 reserve」封进一个方法，5 处统一改用它。

## 待修复 —— 高

### 4. askpass socket 继承 `O_NONBLOCK`（`remote.rs:113`，未复核）

`listener.set_nonblocking(true)` 之后 accept 出来的 socket 在 macOS/BSD 上继承 `O_NONBLOCK`，
`SO_RCVTIMEO` 随之失效，`read_line` 恒返回 `WouldBlock` 被 `continue` 吞掉。accept 在 TCP 握手
即返回，早于 askpass 子进程写出 JSON，读取输给竞态且不重试。后果：任何需要输入密码、加密私钥
口令、或首次确认 known_hosts 的服务器都连不上，`ssh-prompt` 事件永不触发、对话框不出现，唯一
反馈是 150s 后的「SSH 操作超时」。子代理称用独立 Rust 程序在本机实测复现（`code: 35`）。

### 5. 分块上传用短读当 EOF（`remote.rs:614`，未复核）

`if len < 64 * 1024 { break; }`。`Read::read` 合法地可以返回少于缓冲区的字节而并未到 EOF
（EINTR、FUSE/SMB/NFS/iCloud 卷）。截断后 `upload_finish` → `prepare_local` →
`install_catalog_skill` 是拿截断副本和自己比哈希，所以校验通过，用户看到「已上传」而服务器上
是坏的。现有唯一上传测试只发单个子块大小的文件。

### 7 + 9 + 事务层同族（未复核 / 已复核）

这一族根因相同，子代理认为可一并关掉：

- `skill_files.rs:270` 是唯一在 `begin()`/`commit()` 之间用裸 `?` 的调用点，而 `Transaction`
  没有 `Drop`，失败会留下 journal，令 `delete-skill`/`restore-backup`/`purge`/`migrate` 在
  本次会话内全部报「存在待恢复的文件事务，请重启应用后重试」。其余 9 个调用点都用
  `(|| {...})()` 包住并显式 `rollback`。
- `transaction.rs:148` 回滚循环里裸 `?`，一个条目恢复不了就直接返回，剩下的不再恢复、journal
  也不删；下次启动 `recover()` 跑同一个 `finish()`、同样失败。
- `transaction.rs:133` `commit()` 把 `finish()` 失败降级为 warn 并返回 `Ok`，「成功」的操作
  可能留下卡死该功能的 journal。
- `transaction.rs:165` **已复核**：`finish()` 结尾用反序列化出来的 `self.journal` 而非实际
  读取路径 unlink，仓库被 clone 或改名后 → NotFound → Err → 经 `studio.rs:89` 上抛，启动退到
  兜底。第 1 条的修复已让 family B 的这种情形变成 warn+跳过（不再致命），**family A 仍受影响**。

建议的统一修法：给 `Transaction` 加 `Drop`（回滚）、`begin()` 就地恢复而不是要求重启（它已持
有排他锁，就地恢复是安全的）、回滚循环收集错误而不是首个即返回。

### 10. prune 把「目录不可达」当「skill 全被删」（`studio.rs:1124`，未复核）

`scanner::scan_root` 把 `ErrorKind::NotFound` 映射成 `Ok(Vec::new())`，不可达与空目录无法区分。
`hubDir` 指向外置盘时拔盘再点「清理失效引用」，30 个 skill 的分组成员、项目绑定、注册关系与
备注会被永久剥掉。两个加重项：`config.rs:243` 的 `skill_meta.retain(...)` 没有累加 `pruned`，
只毁备注时返回 0、界面还提示「没有失效引用」；`skill_provenance`、`skill_installations`、
`active_groups[].skill_ids`、`policy_suspensions`、`projects[].managed_entries` 从不被过滤，
会留下悬空 id。

### 11. 兜底把 store 换成 `.recovery-scratch`（`lib.rs:125`，未复核）

config 损坏时 `AppState::bootstrap(Store::new(config_dir.join(".recovery-scratch")))`，于是错误
横幅指向的备份恢复 UI 读的是空的 scratch 目录（显示「暂无备份」），而 Hub 相关操作会把用户
真实的 skill 目录**移进**这个隐藏目录；`restore_backup` 也写在那里，于是「恢复成功」而重启后
依旧坏。Err 分支还从不调 `watcher::spawn`。同一表达式上的 `.expect` 在配置目录不可写（例如
曾经 sudo 跑过导致 root 所有）时会直接 panic 在 setup 里，连窗口都没有。

### 12. `reserve` 后 `atomic_write` 同一路径（`manual_policy.rs:150`，未复核）

`tx.reserve(&path)` 已把文件 rename 走，`atomic_write_with_unix_mode` 里
`else if let Ok(meta) = fs::metadata(path)` 因而失败、`set_permissions` 不被调用，临时文件保持
`create_new` 的 0644 被 rename 就位。用户 `chmod 600` 过的 `~/.claude/settings.json`（可能含
env var 与 API key）在每次手动策略 reconcile（每次 scan 都跑）和每次分组切换时被静默放宽。
`agent_groups.rs:352-354` 同一形状。`bytes` 还是在 reserve **之前**读的，中间被 agent 改写会丢。

与第 3 条同源（`reserve` 挪走目标后，后续对该路径的读取全部失效），但第 3 条的修复只解决了

### 13. `fs::read` 无大小上限（`tokens.rs:111`，已复核）

`estimate_file` 用 `fs::read(path)` 把文件整体读入，无上限；而同项目 `scanner.rs:372-389`
同类读取有 1 MiB 的 `LIMIT`。`walk_extras` 递归到 `MAX_SCAN_DEPTH` 对每个非点文件调用它，
`estimate_skill` 又由 `build_skill` 对每个 skill 每次 scan 调用，而 scan 由 400ms 去抖的
watcher 触发。skill 目录里放进一个数 GB 的文件即每次刷新分配同等内存；因为开机后就会
`scan_with_policy`，应用会崩溃循环而用户进不了界面去删那个文件。改成
`File::open(...).take(LIMIT)` 即可。

### 14. `mutate()` 先改磁盘再落盘（`state.rs:57`，未复核）

`f(&self.studio, &mut next)?` → `save_config(&next)?` → `*guard = next`。闭包里的文件系统操作
已完成并把成功记录进 clone；若落盘失败（磁盘满、config.json 无法 fsync/rename），`?` 提前返回，
`*guard = next` 不执行，内存与磁盘的记录一起被丢弃，而磁盘上留下 config 不认识的副本：
`unregister` 找不到可移除项、`prune` 看不见、`scan_skills` 把它们当手动条目，而
`reconcile_manual_policy` 可能把它们原生停用。该方法的 doc 声称的是相反行为
（「落盘失败会把内存里的改动一起报错返回」）。`project_write`/`marketplace`/`manual_policy`
靠把 config_path 纳入自己的 journal 规避了这点。

### 15. `copy_exact` 与 `dir_content_hash` 对软链口径不一致（`skill_files.rs:276`，已复核）

口径分歧在 `copy_exact`，暴露点在 `skill_files.rs:196` 那句 `dir_content_hash(path)? != before`。

`copy_exact`（`:283-286`）`read_link` 后按**原始链接文本**重建；`dir_content_hash`
（`scanner.rs:178-181`）走 `link_destination` **解析**后记成 `external:{target}`。含相对外链的
skill（如 `lib -> ../shared/lib`）在源位置与备份位置解析出不同结果 → 哈希不等 →
`stash_skill` 报「备份时源文件发生变化」而其实什么都没变，`restore_skill_backup` 同理。
后果是这个 skill 永远删不掉也停不掉。测试只用绝对软链，覆盖不到。

### 16. `normalize_path_lexically` 的 `..` 弹栈（`paths.rs:68`，已复核 / 代码推演）

`ParentDir` 分支 `if !normalized.pop()`：第二个 `..` 会把前一个刚 push 进去的字面 `..` 弹掉。
`normalize("../../a/b")` 得 `"a/b"`，于是 `is_same_path("../../a/b", "a/b")` 为真、
`path_is_within("a", "../../a/evil")` 为真。主要调用方大多先 canonicalize，且
`checked_skill_path` 另外拒绝 `ParentDir`，所以它是一层**失效的纵深防御**而非直接漏洞。
现有测试只用 `skills/../../evil`（归一化成 `../evil`），照不出这个 bug。

> 此条基于 `PathBuf::pop()` 语义推演（`Path::new("..").parent() == Some("")`，故 pop 返回
> true 并清空），未实际运行断言确认。补一行测试即可定论。

### 17. `.DS_Store` 锁死换 Hub 目录（`settings.rs:161`，已复核）

`old_hub.exists() && read_dir(old_hub)?.next().is_some()` 数的是全部 dirent，包括
`scanner::scan_root`（`scanner.rs:306`）刻意跳过的点文件。在 Finder 里打开过一次 Hub 目录
（产生 `.DS_Store`）、又已移出全部托管 skill 后，换 Hub 会报「当前 Hub 非空或有启用中的
分组，请先移出或剔除已托管的 skill」，而界面上一个 skill 都没有、也从不显示点文件。回滚过的
Hub 事务留下的 `.xxx.backup-<pid>-<nonce>` 兄弟文件、或中断的原子写留下的 `.tmp.` 文件同样
会触发。应当只数 `scan_root` 会数的东西（非点目录）。

> 严重度不高：用户能从终端删掉那个文件自救。

### 18. `upload_local_skill` 不在 handler 列表（`LocalSkillsPanel.tsx:91`，已复核）

走 `nativeInvoke` 并抛出原始的 "Command upload_local_skill not found"，直接显示在
`<p role="alert">` 里。唯一防线是 `{target.id !== "local" && …}` 的渲染守卫。

> 附带问题（独立于本条，值得单独修）：`ipcContract.test.ts:93` 只扫 `src/lib/api`，于是这个

## 根因

四条泄漏的假设，前三条由子代理归纳、我复核后同意，第四条是修第 2 条时补上的：

1. **日志内容被当作可信输入**（1、9）。
2. **`reserve()` 把目标 rename 走之后，后续对该路径的读取全部失效**（3、12，以及 8 的点文件
   撞车）。第 3 条的修复只覆盖了备份轮转一处，`manual_policy.rs:150` 与
   `agent_groups.rs:352` 同一形状仍在。
3. **没有 `Drop`、`begin()` 也不做就地恢复**，于是 `begin` 与 `commit` 之间任何提前返回都会
   卡死一个功能直到重启（7、`transaction.rs:133`/`:128`）。
4. **路径比较是词法的，而文件系统不是**（2、16、`paths.rs:86`，以及 15 的解析/文本不一致）。
   项目把「Hub 不得与 agent skills 目录重叠」和「此路径在那个 base 内部」写成安全底线，而这
   两个判断都可以在为假时被满足。第 2 条已修掉其中最要紧的一处。

另外：凡是写操作不在 journal 内（6、14）、或把「不可达目录」读成「空目录」（10、17）的地方，
config 与文件系统就会漂移。

## 附录：`unapply_project` 的语义待定

修第 6 条前需要定一件事。子代理列了三条后果，我复核后认为**第三条站不住**：

> the next apply_project/set_project_enabled(true) still sees demo in skill_ids and silently
> recreates exactly what the user removed

该函数的 doc 写的是「从项目里移除某些 skill 的**注册**」，即撤掉部署的文件，而不是取消选择。
按这个意图，重新 apply 时把文件装回来是**符合设计的**，不是 bug。

另外两条后果确实是 bug，与语义无关：

- `managed_entries` 仍列着文件已不存在的路径 → `project_local.rs:56-59` 报 `managed: true`
- 循环中途失败没有回滚

补充事实，供定夺：

- `projectsApi.unapply`（`src/lib/api/projects.ts:98`）在前端**没有任何调用点**，该命令目前
  只能经 IPC 直接触达；唯一测试是 `migration_safety.rs:135`，且它只断言 `is_all_ok()`，
  从不检查 `managed_entries`。
- 兄弟操作 `set_project_enabled(id, false)` 走的是 `reconcile_project(config, id, None, false)`，
  那条路径是事务性的，并在 `project_write.rs:263` 更新 `managed_entries`。

所以待定的是：`unapply_project` 应当（a）只修 `managed_entries` 与回滚，保留 `skill_ids`
以维持「撤下部署」的语义；还是（b）既然 `set_project_enabled(false)` 已经正确地做了同一件事，
它其实是个 UI 不可达的重复实现，应当考虑收敛掉。
